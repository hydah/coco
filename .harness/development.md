# coco：编码与审查

这份约定约束编码过程；[设计文档](docs/README.md)说明现有实现，[测试要求](testing.md)约束完成前的环境验证。环境矩阵全绿不等于行为推演完整。

## 编码前

改运行时、协程、线程、网络或 TLS 行为之前，先做下面四件事。小改动在任务说明或对话里记录即可，不必为每个任务新建文档；跨模块或公共行为的约定放进对应设计文档。

1. 从直接控制行为的函数开始，读一个最近的调用方或测试，以及对应设计文档。入口只负责转发时，继续到真正决定状态、返回值和资源释放的地方，不先扫描整个仓库。
2. 写清本次必须保持的行为：返回值、状态、线程归属、资源所有者、完成提交点和取消观察点。返回成功、收到取消、资源已释放可能是不同事实，不能只用一个返回码代替。
3. 按下面的风险表选出适用项，列出具体输入或事件顺序、预期断言及对应测试；不适用的项简述原因。至少给出一个能推翻当前实现判断的定向检查，再写生产代码。
4. 修 bug 先让回归测试在修复前因目标行为失败；新行为先写能暴露缺口的测试。若现有设施无法构造反例，明确缺什么及剩余风险，不能用其他测试通过来代替。

## 按改动选择风险

| 改动触发 | 必须回答的问题 | 至少考虑的反例 |
| --- | --- | --- |
| 等待、取消、退出、子协程或回调 | 正常完成、错误、超时、取消、启动失败分别如何退出？错误和取消共存时如何保留？最后一个任务结束是否绕过取消记录？ | 等待前取消、等待中取消、最后任务完成与取消处于同一次调度交接；关键事件交换先后顺序；零任务与部分启动失败。 |
| 资源和线程归属 | 谁持有栈上捕获、socket、netfd 和回调？哪些操作会让出？取消后谁收拢任务，何时才可释放资源？跨线程交接是否合法？ | 清理过程再次让出、重复关闭或停止、对象未启动便销毁；投递已成功但函数尚未完成。 |
| 超时、重试、回退或缓存 TTL | 超时约束单次尝试还是整个操作？使用什么时钟，从何时计时？后续步骤是否只花剩余预算？清理是否另有策略？ | 多次短读、重试与协议回退消耗原预算；截止边界的迟到响应；一个答案已收到、另一任务仍等待时 TTL 到期。 |
| 不可信输入和协议解析 | 响应是否匹配来源及完整请求语义，而不只是 ID？长度、迭代深度、内存、缓存和 CPU 工作量是否都有边界？ | 空包、截断、嵌入 NUL、错误类型或标志、ID 碰撞；上限前一项、上限、上限后一项；环及深指针链。 |
| 配置、缓存或共享状态 | 在途操作用哪份快照？配置更新后旧结果能否写回？测试结束后哪些全局状态必须复位？ | 在途请求与配置刷新交错、过期结果迟到、同进程连续运行；socket 地址中的 IPv6 scope 与配置版本差异。 |

取消一经观察，不能被普通完成或重试意外清掉。是否以取消错误返回，仍按接口契约决定；先明确契约，不在修复时顺手改变已有错误优先级。操作已经完成提交后的取消如何处理，也要划清边界，不承诺无法观察的事件。

ST 协程在同一个 native thread 上也有逻辑交错。TSan 没有告警不能证明这些交错正确。每条退出路径都要核对：状态已记录、返回值符合契约、子任务已结束、资源才可释放；不要把发出中断当作任务已退出。

协议解析除了不能越界和死循环，还要约束最坏输入的工作量。协程默认栈只有 64KB，避免以大栈缓冲区或无界递归换取正常输入下的便利。

| 场景或事件顺序 | 必须保持的行为 | 定向证据或缺口 |
| --- | --- | --- |
| 最后一个子任务中断等待者，随后成功返回 | `TaskGroup::Wait()` 保留子任务结果 `COCO_SUCCESS`；`Cancelled()` 仍为真；组内任务已收拢。 | [TaskGroup 测试](../tests/task_group_test.cpp)中的 `TaskGroupWaitCancelsWhenInterrupted`，分别断言返回值和取消状态。 |
| TCP 回退多次短读，每次都在单次超时内，但总耗时超预算 | 总截止时间不随短读重置。 | [DNS 测试](../tests/dns_test.cpp)中的 `DnsResolverTcpUsesTotalDeadline`。 |

## 实现与定向验证

1. 每次只改能检验当前行为判断的最小范围，优先修直接控制该行为的抽象。不要只在调用方隐藏丢失的状态，也不要把邻近功能一起重构。
2. 首次实质修改后立即跑对应定向检查，再继续读别处或修改下一块。测试失败支持当前判断时修同一处并重跑；推翻判断时沿最近调用关系重新定位。
3. 时序测试优先用现有测试工具、显式中断、通知或握手控制顺序，不以长时间 sleep 或反复碰运气代替构造反例。检查返回值，也检查最终状态、资源收拢和无后续访问；时间断言留调度余量。
4. 定向检查通过后，再按[测试要求](testing.md)跑必要的环境、单进程、安装和 sanitizer 门禁。行覆盖率、分支覆盖率和 sanitizer 各自说明覆盖了什么，不能代替时序断言或互相冒充。

## 完成前审查

审查者需要收到改动范围、行为记录、定向结果和未覆盖项，并直接检查控制行为的代码及最近调用方，而不是只接受实现者的说明。有独立审查工具时使用；没有时做单独一轮反例审查，并说明不是独立复审。

审查至少核对三点：

1. 每个适用风险是否有具体反例和断言；成功、错误、取消及关键事件交换顺序是否遵守契约。对取消问题，同时检查返回值与持久状态。
2. 提前返回、最后一次循环和清理中的让出，是否绕过状态记录、总预算检查或任务收拢；不可信输入是否存在有限但过大的计算量。
3. 测试是否真的控制了声称覆盖的输入或顺序。发现缺陷先补能复现的测试，再修复、重跑和复审；未验证项不得包装为通过。

完成结论先给行为证据和审查结果，再列[测试要求](testing.md)中的环境结果与已知失败。公共行为变化同步设计文档和示例。

发现新的遗漏类别时，在这里补充「触发条件、必须保持的行为、构造反例的方法和回归用例」；不堆叠一次性排障日志，也不只添加「注意边界情况」这样的泛泛提醒。
